A governed front door
for enterprise applications

Use specialist AI agents to prepare and coordinate application access changes, while trusted software enforces permission and people approve when policy requires.

What is ingress?

Ingress is how a user or system reaches an application. It connects the application address, encrypted connection, traffic routing and security checks. A control plane manages those settings; it does not carry the application's live traffic.

Why this matters

These changes cross application, platform, network and security teams. The proposed system gives teams one request, a clear plan, an accountable approval path and evidence that the application works. It aims to reduce manual handoffs and inconsistent changes.

Current status: a working governance and simulation prototype. It is not a production-ready multi-cloud platform. A successful demo does not prove that real infrastructure changed or that real traffic is healthy.

Decision requested

Endorse a gated pilot on one explicitly selected cloud setup, subject to scope, ownership, corporate software approval and a costed delivery plan. Do not authorize general production writes or advertise support for every cloud configuration.

Expected benefits are hypotheses to measure. No onboarding speedup, cost saving, availability level or universal recovery time has been demonstrated.

How the agents work together

A trusted workflow coordinator tracks the work, its deadlines and its evidence. Agents exchange structured findings, not unrestricted instructions. Only independent analysis runs in parallel.

1. Understand the requestIntake confirms the application, target environment, requested access and missing information.
Confirmed request goes to discovery
2. Establish the factsDiscovery collects real routing, network, certificate and application observations, recording their source and age.
The same observations go to the required specialists
Security and policyCheck requirements and flag missing evidence.
Impact analysisIdentify affected applications and conflicting changes.

Findings are combined; mandatory gaps stop the change
3. Prepare and validate the planPlanning proposes the change. Trusted code builds and checks the exact configuration, affected resources and recovery limits.
The resolved plan goes to authorization
4. Decide whether it is permittedPolicy allows an already authorized action, requests human approval or denies it. A human reviews only when required.
Only a currently authorized plan proceeds
5. Deliver through the approved ownerA separately credentialed executor rechecks permission and current state, then submits the exact change through the chosen deployment system.
Submission is not completion
6. Prove the result, or recoverIndependent checks confirm application access and security behavior. Unhealthy results trigger authorized recovery or a clear operator escalation.

Agents do the permitted work end-to-end. Humans set automation limits, approve exceptions when required and resolve cases the system cannot safely complete. AI neither grants permission nor sits in the live traffic path.

Multiple agents are useful for distinct expertise and independent investigation. More agents are not automatically safer or faster; compare them with a simpler baseline during the pilot.
Accountability and safety | 3 of 7

When does a person need to approve?

Security and platform owners define an automation envelope: which targets, actions and limits may run without a new approval, and for how long. The system checks policy against the actual plan and again before a change.

Already authorizedProceed only inside the approved scope, limits and expiry.
Human requiredPause for an authorized reviewer; separate requester and reviewer where policy requires.
DeniedStop. Approval cannot override a mandatory prohibition or unsupported capability.

A concrete example

A team requests a public address for its application. Agents check the selected cloud setup, encrypted access, security filtering and application health, then prepare a plan. If policy requires review, the reviewer sees the exposure, impact and recovery limits. After authorization, the system deploys, verifies real traffic and reports the outcome.

What an approval must show

The exact target and change; why approval is needed; affected users and resources; evidence age; automatic stages that follow; recovery limits; and approval expiry. A materially changed or stale plan must be re-evaluated.

Required safeguardWhat it means in plain language
Separate permissionsAnalysis cannot write infrastructure. The executor receives only narrowly scoped authority; a prompt is not a security boundary.
Bound authorizationPermission applies to a specific plan and target, not anything the AI decides to do later.
Fresh-state checksConflicting changes or stale evidence stop the affected work rather than overwrite another owner's settings.
Protected recordsRetain decisions, versions, operation receipts and verification evidence. The prototype's local hash chain is not a complete production audit control.
Bounded failure handlingLimit attempts and waiting. On timeout or a lost response, establish what happened before retrying a possibly completed change.

No instant-recovery promise. Some changes cannot be undone immediately. Address caches, cloud operations and certificate issuance can take time. Cancellation does not undo a request already accepted by a cloud service.

The operator view must distinguish simulated, observed, waiting, failed and unknown results, with a reason and next safe action. A heartbeat or animation is not evidence of completed work.

These are production requirements to implement and verify, not guarantees established by the current prototype.

What multi-cloud support will mean

AWS, Azure and Google Cloud are initial targets, not certified coverage. Select one cloud first, then qualify one explicit setup per cloud. Each qualification names the products and versions, region restrictions, public or private access, security features and allowed deployment methods.

The initial scope is Kubernetes-backed HTTPS applications: application address and routing, network prerequisites, encrypted access, certificates, security filtering and real health checks. Other clouds, specialized protocols, serverless applications and multi-region recovery require separate evidence.

Extensible does not mean unrestricted

A new integration must implement the shared contract and pass compatibility, permission, failure and recovery checks. New specialist configurations may reuse already approved read-only tools; new executable tools or cloud permissions require review and qualification.

Proof of reuse: Add a second qualified cloud setup without redesigning the core approval, authorization or recovery process. Unsupported requests must be explained and stopped, not silently changed.

The core owns coordination and authorization rules. Integrations translate approved work into each cloud's real behavior. Product limitations do not disappear behind a common interface.

Where responsibilities and permissions sit

One operating core coordinates specialists, policy and execution. Analysis, verification and infrastructure writes use separate permission scopes, even when built from the same codebase.

Keep the traffic path separate: Users reach the cloud front door and application directly. Neither AI nor the workflow coordinator handles their live requests. Trusted plan compilation and validation are expanded on the next page.

Proposed production architecture, not the current deployment. PostgreSQL, Temporal, OPA, credentials and cloud integrations remain subject to the delivery gates.

Leadership decisions before delivery

  • Sponsor and scope: Select the first application/cloud setup; name platform, security, network/certificate and recovery owners.
  • Authority: Approve who may set automation envelopes, review changes and authorize recovery; agree outage behavior.
  • Investment: Require a costed, time-boxed pilot and corporate approval of software, hosting, data handling and support.

Measure value before expanding

Compare request-to-verified-service time and manual effort with today's process. Track successful changes, rejected unauthorized actions, unknown outcomes, user-visible recovery time, operating cost and operator comprehension. Agree numerical targets before the pilot; report observations rather than simulation values.
